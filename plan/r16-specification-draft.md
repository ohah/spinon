# R16 · 스피논 명세 초안과 첫 적합성 시나리오

**상태:** 계획 · **공식 항목:** R16 · **계약 숫자 버전:** `0.1.0-draft` 유지

## 목표와 경계

현재 `spec/0001`–`0008`에 흩어진 공개 계약의 범위·버전을 인덱싱하고, 아직 결정되지 않은 제품 계약을 구체적으로 드러내며, 첫 적합성 시나리오의 작성 형식을 정한다. 새 런타임 동작, 안정 API 또는 제품 지원은 이 작업에서 선언하지 않는다. R16은 명세 초안과 시나리오 제안의 완성만 판정한다.

현재 공식 기준은 [명세 인덱스](../spec/README.md), 각 제안 계약, [API 명세 목록](../spec/api/README.md), [구현 상태 대장](../spec/STATUS.md), [내부 명세 인덱스](../spec/internal/README.md)다. 기준 구현은 저장소의 고정 fixture·실행 근거와 해당 작업에서 지정한 Chromium 또는 플랫폼 동작이며, Spinon 구현 스스로만을 유일한 oracle로 사용하지 않는다.

## 구현 전 비교 모델

- **기준:** 위 명세 파일과 현재 `origin/main`의 상태 대장 간 교차 일관성. 시나리오가 특정 동작을 인용할 때는 해당 공개 제안 계약과 기존 고정 fixture·원본 실행 근거를 함께 대조한다. 실행 근거가 없는 동작은 `미실행`으로 남긴다.
- **입력:** 명세 ID·제안 버전·문서 소유 경계, 해당 상태 대장의 상위/하위 작업 ID, 각 시나리오의 고정 fixture 또는 명세 출처, 플랫폼·빌드·엔진 조건.
- **관찰값:** 문서 ID와 버전, 지원 상태, oracle·입력·기대 결과, 오류/진단, 플랫폼 행렬, 근거 링크와 실행 결과 상태.
- **판정:** 문서의 각 계약은 정확히 하나의 규범 소유 문서를 갖고, 지원 표기와 실제 상태 대장이 모순되지 않아야 한다. 시나리오는 `제안/미실행`을 기본값으로 하며 구체적인 통과 증거가 있을 때만 플랫폼별 `통과`를 쓴다. 기존 구현 근거만으로 공개 API 지원을 승격하지 않는다.
- **독립 확인:** 문서 교차 링크 검사와 RSPress 문서 빌드, 별도 파일 기반 adversarial review. 런타임 시나리오 결과는 이 문서 변경만으로 만들거나 추정하지 않는다.

## 산출물 범위

1. 새 공개 문서 `spec/0009-conformance-scenarios.md`에 시나리오 필드, 결과 상태, 버전 정책, 플랫폼별 판정 규칙을 둔다.
2. 기존 `0001`–`0008`의 ID·제안 버전·소유 범위·미정 경계를 한 표에 정리하고 문서 간 중복 규범이 생기면 소유자를 표시한다.
3. 첫 시나리오 제안은 다음 일곱 개의 end-to-end 경계를 다룬다: 초기 UI 트리/표시, 제한 CSS layout·paint, 입력과 문서 변경, 비동기 callback/commit 순서, 미지원 기능 진단, surface/lifecycle 재생성, 접근성 이름·활성화. 각 시나리오에 계약 출처, fixture 후보, oracle, 수집할 값, 플랫폼 행, fail 조건, 미실행/미지원 경계를 적는다.
4. `미정` 등록부에는 미결 질문, 소유 명세, 사용자/후속 작업의 결정 지점, 결정 전 차단되는 지원 주장을 기록한다. R16에서 결정을 임의로 확정하지 않는다.
5. 각 기존 공개 명세의 버전 표기를 감사한다. 누락된 표기만 `0.1.0-draft`로 맞추고 계약 숫자 버전이나 출시 정책은 바꾸지 않는다.
6. 시나리오 상태와 제품 API 상태를 별도로 둔다. 기존 `spec/api/index.md`의 지원 API 수 `0`을 유지하고 R16을 제품 구현 완료로 해석하지 않는다.
7. `spec/README.md`, `spec/0001-conformance.md`, `spec/STATUS.md`에서 새 문서를 연결한다. R16만 문서 산출물 완료로 표시하고 C/S/API 상태는 바꾸지 않는다.

## 명시적 비범위

- 첫 공식 릴리스 범위, 공개 API의 지원 버전, 최소 Android/iOS OS, 시각 허용 오차, 접근성 허용 기준, framework/bundler 행렬을 결정하지 않는다.
- 시나리오 runner, CI job, WPT 결과, 새 API 문서나 runtime code를 추가하지 않는다.
- 기존 시뮬레이터 또는 브라우저 결과를 새로운 통합 시나리오의 PASS로 합산하지 않는다.
- 기존 제안 명세의 의도된 계약을 이 계획이 임의로 강화하거나 변경하지 않는다. 충돌이 발견되면 해당 항목을 `미정`으로 기록하고 R16 안에서 해결을 가장하지 않는다.

## 시나리오 레코드 필수 필드

각 제안 시나리오는 충돌 없는 안정 ID, 목표 계약/version, 플랫폼·앱·bundle 조건, 고정 입력과 초기 상태, oracle와 고정 버전, 기대 화면/geometry/event/diagnostic/accessibility 값, 오류·취소 조건, 수집 파일·hash, 플랫폼별 결과(`미실행`, `통과`, `실패`, `차단`, `해당 없음`), 그리고 해석 한계를 포함한다. 여러 플랫폼은 하나의 결과로 합치지 않는다. `해당 없음`과 `미실행`에는 이유를 적는다.

## 통과 기준

1. `spec/README.md` 인덱스 표와 `spec/0001-conformance.md`가 `0009`의 제안/미실행 상태를 연결하고, 0001–0008의 문서 ID·버전·책임이 빠짐없이 카탈로그에 나타난다.
2. 일곱 시나리오 각각에 필수 필드가 있고, 입력·기대값을 실행 전에 정할 수 있으며 oracle이 측정 대상 구현과 독립적이다.
3. status와 API index는 제품 API 0개와 명세 제안 상태를 그대로 보존하고, 실행 증거가 없는 플랫폼을 PASS 처리하지 않는다.
4. 계약 간 충돌·결정되지 않은 항목은 새 계약으로 덮지 않고 문서와 상태 대장에 명시한다.
5. 추가하거나 변경한 Markdown 내부 링크가 저장소 파일을 가리키고 `mise exec -- bun run docs:build` 결과에서 R16 신규 링크 오류가 없다. 기존 dead-link 보고는 기준선과 분리한다.
6. 계획 검토 20개와 구현 후 검토 20개, PR 변경 검토 20개는 서로 다른 관점과 근거를 사용한다.

## 작업·PR 게이트

- 계획 자체를 구현 전에 별도 20개 실패 관점으로 검토하고, 이 계획 PR에는 또 다른 20개 변경 관점을 적용한다.
- 계획 PR이 병합되기 전에는 R16 산출물 문서에 구현하지 않는다.
- 구현 후에는 문서 소유 경계, 잘못된 지원 표기, 불완전한 시나리오 oracle, 상태표 누락, 링크/빌드 실패를 포함한 새 20개 구현 관점으로 검토한다.
- 구현 PR은 template에 따라 `documentation`, `area: docs` 라벨을 사용하고, 변경 상태 ID·명세·근거·남은 범위를 쓴다. 화면 동작이 없는 문서 산출물이므로 앱 화면 이미지는 첨부하지 않는다.
- 병합은 GitHub `Rebase and merge`만 사용한다. 병합 후 main 문서의 상대 링크와 Tailnet 미리보기의 R16 상태를 Agent Browser에서 확인한다. Pages 배포는 시작하지 않는다.
